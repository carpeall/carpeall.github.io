SQL注入原理及介绍

一. 什么是SQL注入

SQL注入是黑客利用网站的输入框,输入事先定义好的SQL查询语句,而网站又没有对输入进行数据合法性的过滤或者判断,导致这一串输入欺骗了数据库服务器来执行了一系列非授权的查询来得到想要的数据信息

二. SQL注入产生的条件

  1. web网站需要使用数据库

  2. 传递给后端的参数可以控制,可以控制输入信息

  3. 变量未存在过滤或者过滤不完全

  4. 参数内容会被带入到数据库进行查询

三.SQL注入危害：

1 - 数据库信息泄露

2- 网页篡改：通过操作数据库对特定网页进行篡改，嵌入网马链接，进行挂马攻击。

3- 数据库被恶意操作：数据库服务器被攻击，数据库的系统管理员帐户被更改。

4- 服务器被远程控制：黑客可以修改或控制操作系统。

5- 种植木马：瘫痪全系统。

四.SQL注入常用函数：

version()mysql版本

database()数据库名

current_user()当前用户名

@@datadir数据库路径

@@basedir数据库安装路径

五. SQL注入漏洞分类体系

1.数据库类型

1) 分类

关系型数据库(SQL):Access、MySQL、Oracle、PostgreSQL、SQLite、MSSQL

使用SQL语句注入

非关系型数据库(NoSQL):MongoDB

使用JSOn格式查询对象

2) 介绍

Access:微软 Office 套件自带小型桌面数据库,整个库是一个.accdb文件
MySQL:MYSQL是一款开源免费的关系型数据库管理系统(RDBMS)
Oracle:甲骨文商用顶级企业级关系数据库
PostgreSQL:简称 PG，号称最标准、功能最全的开源关系库
SQLite:零配置嵌入式文件数据库,无服务进程，数据库只是单个 .db 文件，内置在程序代码里
MSSQL:微软出品商用关系数据库
MongoDB:唯一一款 NoSQL 文档型数据库,存储格式为 JSON 类文档（BSON），无固定表结构

2.提交方法

1) get注入

原理:注入点位于URL的查询参数中.

2) POST注入

原理:注入点位于POST请求中,通常是登录表单,搜索框,留言板等

3) Cookie注入

原理:注入点在cookie头中.有些应用会把cookie值不做任何过滤就拼接到SQL语句中

4) Request注入

原理:不是发一个新的请求，而是把一次真实的 HTTP请求完整保存到文件，然后让工具读取这个文件来分析注入点。文件包含了该次请求的所有细节

5) Http头

原理:对User-Agent(用户代理),Referer(来源页),X-Forwarded-For(客户端ip),cookie和Host头写入注入语句

3.数据类型

1) 数字型

特征:参数值直接以数字形式拼接到SQL语句中,没有引号包裹
判断方式–用数学运算检测是否被当做数字解析
  • id=2-1 与 id=1 返回相同
  • id =1 AND 1=1 正常,id=1 AND 1=2 异常
  • 加单引号 id=1’ 直接报错

2) 字符型

特征:参数值用单引号或双引号包裹后拼接到SQL语句中
判断方法
先闭合前面的引号,再注入自己的逻辑,最后处理多余的引号
1.单引号测试
?id=1’
如果页面报错或者返回异常,说明单引号破坏了SQL语句结构->大概率的单引号闭合
如果页面正常显示,说明单引号可能不是闭合符,或者被过滤了
双引号测试
?id=1”
同理,如果报错就说明双引号参与了闭合
2.通过报错信息直接判断
单引号报错示例
看到’’’这种三单引号叠加在一起的情况,单引号闭合
双引号报错测试
看到””这种,双引号注入
3.通过注释符来推断
如果直接加单引号没反应(被过滤了),可以用闭合夹注释来推断
假如是单引号闭合
?id=1’ –+
?id=1’
假如是双引号闭合
?id=1” –+
?id=1”
逻辑,如果’ –+ 能让页面恢复正常,那闭合符就是单引号;同理” –+ 恢复正常就是双引号
4.通过括号+引号组合判断
有时引号外面还包括了括号
5.在判断引号之前,先确认是不是字符型

3) 搜索型注入

特征:参数值被用在like模糊查询中,通常用’%’或引号包裹
页面特征:输入部分关键字就能匹配出结果,有明显的搜索功能
判断方法
1.直接观察特征
搜索型注入只出现在搜索功能中
2.用报错信息判断
测试payload
?keyword=test%
?keyword=test%’
?keyword=text%”
单引号搜索型报错示例
输入 test%’ 后
注意看 %test%’’’ 一百分号加三个单引号叠加在一起,单引号搜索型
双引号搜索型报错示例
输入 test%” 后
3.通过闭合+注释判断
这是最实用方法
第一步 确认是搜索型
?keyword=test’ #正常?(那可能是数字型或者like中单引号被转义了)
?keyword=test%’ #报错?(百分号破坏了 like语法,大概率搜索型)
如果test’不报错,说明%参与了语法结构,确认是搜索型
第二部 测试闭合方式
假设是单引号搜索型
?keyword=test%’ and 1=1 –+ # 正常？
?keyword=test%’ and 1=2 –+ # 异常？→确认单引号搜索型 ✓
假设是双引号搜索型
?keyword=test%” and 1=1 –+ # 正常？
?keyword=test%” and 1=2 –+ # 异常？→确认双引号搜索型 ✓
4.搜索型专属闭合 payload
单引号搜索型
#用 and 1-1 消耗掉后面的 %’
?keyword=test%’ and 1=1 –+
?keyword=test%’ and ‘1’=’1
双引号搜索型
?keyword=test%” and 1=1 –+
?keyword=test%” and “1”=”1
5.括号+搜索型组合
搜索框后面可能是带括号的like
此时需要先闭合括号
单引号+单括号搜索型
?keyword=test%’) and 1=1 –+
双引号+单括号搜索型
?keyword=test%”) and 1=1 –+
单引号+双括号搜索型
?keyword=test%’)) and 1=1 –+

5.注入扩展

1) 加解密注入

原理:当应用对用户输入的参数先进行加密 / 编码处理，再传入后端拼接 SQL 语句时，明文凭据的注入 payload 会失效。攻击者将注入 Payload 按照目标的加密 / 编码规则提前预处理，提交后后端解密得到恶意 SQL 语句，从而触发注入

2) JSON注入

原理:
参数载体为 JSON：应用接收 JSON 格式的请求数据，解析字段值后直接拼接 SQL，注入逻辑与常规 SQL 注入一致，只是输入载体是 JSON
数据库 JSON 函数注入：SQL 语句中调用了数据库原生 JSON 函数（如 MySQL 的JSON_EXTRACT），攻击者构造特殊 JSON 路径 / 值篡改查询逻辑

3) LDAP注入

LDAP 注入不属于 SQL 注入，是针对轻量目录访问协议（LDAP） 查询的注入攻击，属于广义 Web 注入的扩展，原理与 SQL 注入同源 —— 构造输入篡改查询逻辑。
原理:LDAP 使用过滤表达式做目录查询，当用户输入被直接拼接到过滤语句中时，攻击者通过( ) & | *等 LDAP 特殊字符修改过滤规则，实现越权查询、信息枚举

4) DNSlog注入

原理:属于盲注的进阶利用方式：当注入点无回显（无法直接看到查询结果），且布尔 / 时间盲注效率极低时，利用数据库的网络请求函数，将查询结果作为子域名发起 DNS 解析，攻击者通过 DNS 日志平台间接获取数据

5) 二次注入

原理:攻击者提交的恶意 SQL 语句，第一次入库时被转义处理，不会触发注入；但当应用后续从数据库中取出该数据，未做二次转义就直接拼接进 SQL 语句时，恶意语句被执行，触发注入

6) 堆叠查询注入

原理:数据库支持同时执行多条 SQL 语句，语句间用分号;分隔。攻击者在原有查询后拼接全新的 SQL 语句，可执行增删改、写文件、提权等远超常规查询的操作

7)宽字节注入

GBK编码：
GBK编码是一种双字节编码，其中每个汉字用两个字节表示。这是因为GBK编码采用了区位码的方式表示汉字，每个汉字在GBK编码中都被编码成一个区位码，区位码由一个区码和一个位码组成。
绕过原理：
一个gbk汉字占两个字节，第一个字节（129-254），第二个字节（64-254），当设置gbk编码后，遇到连续两个字节，都符合gbk取值范围，会自动解析为一个汉字，从而把转义字符\ 吃掉。

      5. 1.5.5. 5.注入扩展
        1. 1.5.5.1. 1) 加解密注入
          1. 1.5.5.1.1. 原理:当应用对用户输入的参数先进行加密 / 编码处理，再传入后端拼接 SQL 语句时，明文凭据的注入 payload 会失效。攻击者将注入 Payload 按照目标的加密 / 编码规则提前预处理，提交后后端解密得到恶意 SQL 语句，从而触发注入
        2. 1.5.5.2. 2) JSON注入
          1. 1.5.5.2.1. 原理:
          2. 1.5.5.2.2. 参数载体为 JSON：应用接收 JSON 格式的请求数据，解析字段值后直接拼接 SQL，注入逻辑与常规 SQL 注入一致，只是输入载体是 JSON
          3. 1.5.5.2.3. 数据库 JSON 函数注入：SQL 语句中调用了数据库原生 JSON 函数（如 MySQL 的JSON_EXTRACT），攻击者构造特殊 JSON 路径 / 值篡改查询逻辑
        3. 1.5.5.3. 3) LDAP注入
          1. 1.5.5.3.1. LDAP 注入不属于 SQL 注入，是针对轻量目录访问协议（LDAP） 查询的注入攻击，属于广义 Web 注入的扩展，原理与 SQL 注入同源 —— 构造输入篡改查询逻辑。
          2. 1.5.5.3.2. 原理:LDAP 使用过滤表达式做目录查询，当用户输入被直接拼接到过滤语句中时，攻击者通过( ) & | *等 LDAP 特殊字符修改过滤规则，实现越权查询、信息枚举
        4. 1.5.5.4. 4) DNSlog注入
          1. 1.5.5.4.1. 原理:属于盲注的进阶利用方式：当注入点无回显（无法直接看到查询结果），且布尔 / 时间盲注效率极低时，利用数据库的网络请求函数，将查询结果作为子域名发起 DNS 解析，攻击者通过 DNS 日志平台间接获取数据
        5. 1.5.5.5. 5) 二次注入
          1. 1.5.5.5.1. 原理:攻击者提交的恶意 SQL 语句，第一次入库时被转义处理，不会触发注入；但当应用后续从数据库中取出该数据，未做二次转义就直接拼接进 SQL 语句时，恶意语句被执行，触发注入
        6. 1.5.5.6. 6) 堆叠查询注入
          1. 1.5.5.6.1. 原理:数据库支持同时执行多条 SQL 语句，语句间用分号;分隔。攻击者在原有查询后拼接全新的 SQL 语句，可执行增删改、写文件、提权等远超常规查询的操作
        7. 1.5.5.7. 7)宽字节注入
          1. 1.5.5.7.1. GBK编码：
          2. 1.5.5.7.2. GBK编码是一种双字节编码，其中每个汉字用两个字节表示。这是因为GBK编码采用了区位码的方式表示汉字，每个汉字在GBK编码中都被编码成一个区位码，区位码由一个区码和一个位码组成。
          3. 1.5.5.7.3. 绕过原理：
          4. 1.5.5.7.4. 一个gbk汉字占两个字节，第一个字节（129-254），第二个字节（64-254），当设置gbk编码后，遇到连续两个字节，都符合gbk取值范围，会自动解析为一个汉字，从而把转义字符\ 吃掉。
